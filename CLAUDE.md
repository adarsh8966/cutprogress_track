# CUT OS - working agreement

A private, single-user fitness measurement and analytics platform. The
application measures and computes; ChatGPT is the reasoning and coaching layer.
The Context Pack is the product - everything else exists so that it has
something true to say.

## Never

- Fabricate health data, or fill in a measurement the user did not record.
- Silently infer a missing measurement. An unset value stays unset.
- Overwrite or delete a raw observation. Corrections are new observations.
- Treat missing data as zero. `null` and `0` mean different things throughout.
- Present a health conclusion without the evidence that produced it.
- Store, request or support body photos. There is no image upload and no
  computer vision anywhere in this system.
- Put a secret in a `NEXT_PUBLIC_` variable, or use the service-role key in
  client code.
- Build a fake integration, or claim Health Connect / Bevel works before it is
  implemented and tested.
- Scrape Bevel. Hevy's official API key lives in a server-side environment
  variable and nowhere else. An OAuth refresh token cannot: it is issued per
  user at consent time and is revocable by that user, so it is stored -
  encrypted at rest (AES-256-GCM), with the key in the environment and never in
  the database, never returned to the browser, and destroyed on disconnect.
  That narrowing applies to OAuth credentials alone; a static API key still
  belongs in an environment variable.
- Let an external integration write outside what it owns. Hevy is training only:
  never body weight, measurements, activity, recovery or nutrition. Google
  Health is health, activity, recovery and sleep only: never nutrition intake,
  never an exercise or a set. Both are enforced by a boundary test, not by
  convention.
- Import nutrition intake from anywhere. Calories, protein, carbohydrate and fat
  are entered by hand. No nutrition scope is requested and no integration may
  name a nutrition table. Calories BURNED are a different measurement and do
  arrive from a provider.
- Let an import silently move a value the user entered by hand. A manual
  observation pins that (day, field); the imported one is still stored, still
  has provenance, and is shown as available rather than applied.
- Train an ML model on insufficient data, or ship one that does not beat the
  deterministic baseline.

## Always

- Write tests. Analytics changes need a test that would fail without them.
- Keep `lib/` pure: no Supabase imports, no I/O. That is what makes the engine
  testable without credentials.
- Return `Derived<T>` from every calculation - value, method, inputs,
  confidence, notes. A bare number is not an acceptable output.
- Use TypeScript strict mode. It is on, including `noUncheckedIndexedAccess`.
- Enable RLS on every user-owned table, and grant no delete policy on
  observation tables.
- Keep raw and canonical data separate, and preserve provenance.
- Normalise units at the boundary. Storage is metric: kg, cm, km, kcal, minutes.
- Make imports idempotent, enforced by a database constraint. For an external
  record that means a unique index on (source, external id), so a re-sync
  updates one row rather than writing a second.
- Match an external exercise by stable id, then by EXACT name, then create.
  Never fuzzily. A duplicate is visible and joinable; a wrong merge fuses two
  movements' histories permanently.
- Correlate a workout with a provider's recording by INTERVAL OVERLAP, never by
  date and never by a language model. Two workouts on one day are two workouts.
- Report a heart-rate zone figure with the method that produced it and how much
  of the session it covers. No heart-rate data means no zone minutes - not zero.
- Document calculations, and version models and the Context Pack schema.
- Aggregate days in the user's timezone, never UTC.

## Layout

```
app/            routes (route group (app) is the signed-in shell) + server actions
components/     UI, charts, forms
lib/
  analytics/    pure calculations, all returning Derived<T>
  normalization/units, timezone-correct dates, canonical resolution
  validation/   safety rails
  health/       exercise catalog, paste parser, idempotency
  integrations/ external sources
                  hevy/         client, mapper, writer, sync (training)
                  googleHealth/ scopes, env, oauth, client, registry, mapper,
                                correlate, telemetry, writer, sync (health)
  context/      Context Pack generator
  data/         server-only queries, the canonical rebuild, manual-field pins
    context/    canonical readers the future AI layer calls. No provider name
                crosses this line, and there is no second store.
  supabase/     clients, env, database types
supabase/migrations/   ordered SQL, verified against PGlite in tests
data/exercises/        catalog.json (generated by scripts/build-catalog.mjs)
tests/          unit (pure core) + integration (PGlite: schema, RLS, seed)
docs/           architecture, data model, analytics formulas, ML roadmap
```

## Verification

`npm run verify` runs typecheck, lint, tests and a production build.

Migrations and RLS policies are exercised against real PostgreSQL via PGlite
(WASM, in-process), because Docker is not always available. That proves the SQL
and the policy logic. It does not prove a hosted Supabase deployment works -
say so rather than implying otherwise.

## Regenerating

- Exercise catalog: `node scripts/build-catalog.mjs`
- Seed migration:   `node scripts/build-seed.mjs` (run after the catalog)
- Database types:   `npx supabase gen types typescript --project-id <id> > lib/supabase/types.ts`
  Row shapes must stay `type` aliases, not `interface` - supabase-js constrains
  each Row to `Record<string, unknown>`, and an interface has no implicit index
  signature, which silently resolves the schema to `never`.

## Adding a Google Health data type

One entry in `lib/integrations/googleHealth/registry.ts` - the id, the filter
name, the record type, the scope, the endpoint, the ceilings, the destination
and an `extract`. If the metric is new to CUT OS, also: a `metric_key` value
(alone in its own migration), a `daily_metrics` column, a `METRIC_FIELD` entry
in `lib/data/canonicalise.ts`, and a reader. Nothing else moves.

Add an `identity` hook to the entry only if two points of that type can share a
time AND a recording source - one point per zone over one interval, say. Without
it they mint the same derived id and all but one is refused by the idempotency
index, silently. Most types need none.

A supported type with no destination is not a problem: mark it `UNMAPPED` and
it is fetched, stored whole and surfaced in Settings until somebody maps it.
